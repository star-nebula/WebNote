WebNote · 运转地图 · 2026-11-10

一次运行，从一条链接到一批待确认动作 这是地图，不是契约。契约在 skills/webnote-workflow/steps/ 的 frontmatter 与 runs/_template/；本文与它们冲突时以它们为准（测试会先红）。

调度器（主会话）干确定性的事：判断类型、调工具、写清单、等用户点头。两个角色各拿一个新上下文：提炼、核查。核查只信原文，不信笔记匠。

一次运行的骨架 · 四步

00

采编

调度器 context: none

判断类型 → 调对应工具 → 正文落一份副本，清单只记元信息。

读 用户给的 URL / 文件 / 剪藏
写 runs/<run>/00-采编清单.md + 原文/<ID>.txt
关键针 内容清单表头 · ## 有正文统计 · ## 运行异常
01

提炼

笔记匠 distiller isolated

每页最多 5 条要点，宁少勿凑；每条标出处与来源类型（原文 / OCR / ASR / Vision）。

读 00 + 原文
写 runs/<run>/01-笔记.md
禁止 写正文没有的数字与结论
02

核查

核查官 verifier fresh

三态判定：已核实（直接引用）/ 已核实（转述源）/ 可疑。与笔记匠零共享上下文。

读 01 + 原文
写 runs/<run>/02-核查表.md
关键针 三态表头 · ## 需用户回看的条目
03

确认

调度器 context: none

按你自己的分类体系给去向（没有体系才用兜底四类），汇总成一批「待确认动作」，停住。

读 01 + 02
写 runs/<run>/03-待确认提案.md
禁止 把「建议动作」当成已执行
可疑条目 回修 ≤2 次，不许新增条目

四步的文件名就是顺序（00-collect.md … 03-confirm.md），没有第二份顺序表。加一步 = 加一个 04-*.md，测试读目录。

三种模式 · 看工具能开几个上下文

模式什么时候用怎么跑
A 多 Agent工具支持 subagent（推荐）主会话做 00 与 03；01 / 02 各起一个 subagent。核查必须与提炼零共享。
B 单对话框开不了新会话同对话做 00+01 → 停下 → 用户把产物带到新对话做 02 → 带回 03。细则：skills/webnote-workflow/mode-b-single-dialog.md
C 无损拓存防复制页 / 钉钉飞书云文档 / 登录墙长文只拓存不摘要，走 steps/branches/web-archive.md；要笔记就拓存核验后再单独提炼。

加载阶梯 · 谁在什么时候拿到什么

AGENTS.md
公开入口，各工具按这个名字自动加载。只写"有哪些东西、按路径怎么读、硬边界是什么"，不复述细则。私有事实（本机路径、偏好）在 AGENTS.local.md（gitignore），读完入口立即读它。
skills/*/SKILL.md
只做路由。description 决定自动触发；正文说明什么时候用哪个文件、去哪读细则。改写流程细节不放在这里。
skills/webnote-workflow/steps/00-04
唯一的流程定义。frontmatter 是契约：step / executor / context / reads / writes / forbidden 决定怎么跑；produces / format_needles 决定产出长什么样，与 runs/_template/ 双向断言。
steps/branches/
只在 00 命中时加载的分支卡：image.md(1) / video-audio.md(2) / web-archive.md(3)。处理一个 PDF 不需要知道 ASR 怎么跑。
tools/
确定性加速器：提取、转写、抽帧、OCR、Vision、自检。依赖全可选，缺了只影响对应分支。
bot.yaml
唯一机器清单，只记一件约定表达不了的事：外部技能（skills/browser-skill）的上游仓库、完整 commit、快照日期、文件数。升版用 tools/check_vendor.py --pull。

产出 → 落库 · 闸门在哪

运行期（本地，不进 git）
  • runs/<run>/00-采编清单.md
  • 01-笔记.md
  • 02-核查表.md
  • 03-待确认提案.md
  • 原文/<ID>.txt（正文副本）
→
闸门（第四步的产出）
  • 三态：直接引用 / 转述源 / 可疑
  • 需回看条目单独成节，不塞备注
  • 转述源不可升格为"直接引用"
→
落库（用户点头之后）
  • 正文 → <知识库根>/Resources/<主题>/<来源>/
  • 成稿 → <知识库根>/Knowledge/<领域>/
  • 删除 / 归档 / 发布：一次一条确认

每道切分挡住什么

切分挡住的失败代价
采编 / 确认留在主会话读完正文后再起一个新上下文做分类，只是把同一段读两遍主会话上下文更长
核查官与笔记匠零共享自证不算核查——同一份上下文里，"我写错了"和"我的判断错了"是同一个判断多一次上下文切换
每条要点标来源类型OCR 误识别的数字与 PDF 白纸黑字拿到同样可信度多一份格式约束
落地动作停在确认前删除、归档、发布、写长期记录撤不回来多一道人工确认

三条铁律 · 只在一处定义

正文不凭空编文本来自工具提取或用户已有；没有就如实写"无"。
核查独立核查者不能是撰写者，必须全新上下文。context: fresh。
落地必待确认删除 / 归档 / 发布 / 写入长期记录，逐条点头才执行。

定义处：docs/architecture.md#三条不可逾越。其余文件只写指针——过去两处各写一版，第三条一处是"不改写用户已有文件"、一处是"落地必待确认"，调度器与入口对"闸门是什么"给出的答案不同。
