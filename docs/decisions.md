## 外部技能：副本进仓、真源记在 bot.yaml，exe 版本号不算真源

**问题**：`browser-skill` 来自腾讯的 `Tencent/BrowserSkill`（MIT），既不由本仓维护，也不是技能库维护的——技能库那份是 2026-09-30 从 bsk 产物人工搬进去的快照。链条是三跳：上游仓库 → `crates/bsk-cli/skill/` → 技能库 → 本仓 `skills/browser-skill/`，最后一跳当时用 `.skillshare` 的 `mode: copy` 镜像。

**发现**：查上游时发现我们落后一代。上游 2026-11 起把单文件 `SKILL.md`（229 行 / 11,406 B）改成「主体 131 行 + `references/` 13 个文件 / 81 KB」，上游 `crates/bsk-cli/src/skill_install/` 里的 `legacy-digests.txt`、`provenance.rs`、`sync.rs` 就是这次布局迁移的痕迹。

**决定**：

1. **真源写进 `bot.yaml` 的 `vendored:` 段**（`upstream` / `subdir` / `ref`（完整 commit sha）/ `snapshot` / `layout` / `files`），因为本地镜像配置只描述「从哪里 copy」，说不清「上游是哪一代」。
2. **不用 `bsk --version` 当基准**：别人机器上不一定有那个 exe，而且 exe 与仓库本来就可能不同代。
3. **检查分两层**：`tools/check_vendor.py`（离线：副本存在、是真目录不是链接、文件数与 `bot.yaml` 一致；进 CI）与 `--online`（按记录的 ref 拉上游 tree API 逐个比 blob sha，并报上游 HEAD 是否前进；联网、可能限流，不进 CI）。
4. **副本按上游布局整体覆盖**，不只换 `SKILL.md`——主体里引用了每个 references 文件，只同步一半会让 agent 读到悬空引用（`test_vendored_references_all_reachable` 守着这条）。
5. ~~**库那一跳保留**：skillshare 的 `include` 按 `<name>/SKILL.md` 找技能，上游是 `crates/bsk-cli/skill/SKILL.md`（目录名 `skill`），直连需要先改名，比中转更绕。同步时两份一起换，否则下次 `skillshare sync -p` 会把副本退回旧版。~~ **已推翻（2026-11-10）**，见下。

**代价**：仓库多 88 KB 与 13 个文件；`--online` / `--pull` 依赖 `gh` 或 `GITHUB_TOKEN`（匿名 API 会 403 限流）。

**修订（2026-11-10）：删掉 `.skillshare/`，改上游直取**

上面第 5 条把「本地中转」当成了省事，实际反了：

- 中转那一跳（技能库 `E:\Agent\skills\browser-skill`）既不是本仓维护，也不是上游维护，却是链上唯一「谁都没责任更新」的一环；
- 它把真源方向倒置了——`skillshare sync -p` 是从库往仓复制，库没更新时跑一次就静默回退（`docs/README.md` 当时自己就写着这句警告）；
- 维护成本落在人身上：升版必须两份一起换，漏一份等于白做。

现在只有两跳：上游 `Tencent/BrowserSkill` → 本仓 `skills/browser-skill/`。`check_vendor.py --pull` 拉上游 HEAD 的 tree、按 blob sha 下载原始字节整体覆盖、删掉上游已没有的文件，并把 `ref` / `snapshot` / `files` 写回 `bot.yaml`。`--online` 改为对照**记录的代际**，因此它同时回答两个问题：副本有没有被手改、上游有没有前进。

测试相应改为断言「副本是真目录、无链接、`.skillshare` 不许回来、文件数与 `bot.yaml` 一致」。代价：升版需要 `gh` 登录或 `GITHUB_TOKEN`；不再有本地离线镜像源。

## 记忆分层：核心记忆进 AGENTS.md，长期记忆进 memory/

**问题**：`persona/SOUL.md` 与 `AGENTS.md` 内容重叠（身份、专职角色、硬约束、汇报格式各写一遍），且 SOUL 里的落库路径还是错的（`<知识库根>/vault/Resources/`（`vault/` 早已不存在））。同时没有任何地方沉淀"跨 run 的经验"——都散在 `runs/`（过程）和知识库（产出）里。

**决定**：

1. **核心记忆不单独建文件**，写进 `AGENTS.md` 的「核心记忆」小节（私有块内）。理由：它必须常驻上下文，多一个文件就多一次读取、多一个漂移点，而 `AGENTS.md` 本来就是被自动加载的那一份。`persona/SOUL.md` 内容并入后删除（原稿在归档包 `webnote-role-2026-11-09.tgz`）。
2. **长期记忆独立成 `memory/`**：`index.md` 一行一条做检索，`long-term/` 一条一文件（frontmatter 标 `date/topic/confidence/source`）。理由：记忆要按需取，整目录塞进上下文只会稀释注意力；一条一文件也让"索引腐烂"可被测试发现。
3. **角色与技能不做合并**：`agents/` 与 `skills/` 的位置是被工具机制钉住的（`skills/<name>/SKILL.md` 是发现约定，`AGENTS.md` 是入口文件名），搬家即失去自动发现。只有长期记忆没有任何约定，才需要人为给它一个目录。
4. 边界：`runs/` 是过程不是记忆；记忆只从 `03-核查表.md` 这类已核实的产物里提炼，且落盘要用户点头。角色（subagent）不得写记忆。

> 后续（2026-11-09）：`memory/` 已删除，跨 run 结论只落知识库，见下方「清减」条目。

**代价**：多一层目录与一条索引维护成本；换来"下次怎么做得对"有确定落点，且不用把整份历史塞进上下文。

## 角色分发：真源 + 生成物，写入边界挂在项目级 hook

**问题**：同一个角色定义要同时喂给多种 agent 工具，而各工具的注册面互不兼容；手写多份薄壳后，`description` 会漂移，且薄壳里写的 `permissions.allow/deny` 在 Claude Code 里根本不是可用字段（实测 CC 2.1.310 只解析 `name/description/prompt/tools/disallowedTools/model/effort/permissionMode/mcpServers/hooks/maxTurns/...`），"核查官只能写 03-核查表.md" 因此毫无机制保障。

**决定**：

1. 角色定义只有一处 —— `agents/<name>.md`（含 `description` 与 `context/reads/writes/forbidden` 契约），平台无关。
2. 注册信息只有一处 —— `bot.yaml`（`tools` / `disallowed_tools` / `write_scope` / `fresh_context`）。
3. `.claude/agents/*.md` 与 `.claude/settings.json` 是**生成物**，由 `tools/doctor.py --wire` 产出，CI 用 `--check` 打回手改。
4. 写入边界不依赖 agent frontmatter 的 `hooks`（实测不执行），改挂项目级 `PreToolUse`：`tools/hooks/guard_write.py` 读 payload 里的 `agent_type`，按 `bot.yaml` 的 `write_scope` 判定，越界 exit 2。

**代价/收益**：多一个生成步骤与一条 CI 断言；换来一份定义喂所有工具，且"越界写入"从提示词约束变成机制拦截（实测 verifier 写 `runs/x/02-笔记.md` 被拒、`runs/x/03-核查表.md` 放行）。

> 后续（2026-11-09）：注册面整体退役（`doctor.py`、写入守卫、`.claude/agents/`、`bot.yaml` 的 roles/skills/flows 全部删除）。原因见下方「清减」条目——它只对一家工具生效，换工具即失效。

## 2026-11-10 · 五步合一：流水线定义只留一份

**问题**：同一个五步流程被写在四个地方——`docs/architecture.md` 的顺序表、`skills/webnote-workflow/SKILL.md` 的派发表、`references/steps/` 的五张卡、`agents/` 的三份角色定义，外加 `runs/_template/` 的表头。审计实测：改一步的上下文要求要动 3 处（其中 2 处会漏，`AGENTS.md:24-25` 的独立上下文表就与 `agents/*.md` 的 `context: isolated` 相反）；加一步要动 9 处。`references/steps/` 还自称"五步"却只有采编与确认，角色在隔壁——"五步"这个概念本身没有对应物。

**决定**：`skills/webnote-workflow/steps/` 是流水线的唯一定义处。

1. `00-collect.md` / `01-classify.md` / `02-distil.md` / `03-verify.md` / `04-confirm.md`，**序号由文件名表达**，不另设顺序表；采编分支卡收进 `steps/branches/`。
2. 角色属性进步骤文件 frontmatter（`context` / `reads` / `writes` / `forbidden` / `produces` / `format_needles`）。`agents/` 目录删除——它的三个文件本来就是这三个步骤本身。
3. 产出格式针（表头、必备小节）写进对应步骤文件的 `format_needles`，`tests/test_repo.py` 从它派生比对 `runs/_template/`。**规范成了测试的输入，而不是测试的旁注。**
4. 铁律只在 `docs/architecture.md` 定义一处，`AGENTS.md` 与 `SKILL.md` 只留指针，并由测试拦住废弃版本回流。

**为什么不是别的方案**：
- 「加一份 `pipeline/00-05.yaml` 顺序表」会新增第五份副本，还是要人同步——维护成本不降反升。
- 「保留 `agents/` 只删 `references/steps/`」仍需两处改 `context`，且 `steps/` 无法说清"每步谁执行"。
- 「角色与步骤拆成 `roles/` + `steps/`」是当前四处的等价重排，只是换了名字。

**代价**：
- 步骤文件同时是"给调度器读的操作卡"和"给 subagent 读的角色契约"。两份读者读同一个文件——但这是有意的：subagent 本来就需要知道调度器会给它什么、它必须交回什么。
- 序号是文件名的一部分，重排步骤要改名（5 个文件），换来的是一条人人可读的顺序。
- 分支卡与主步骤同在 `steps/` 下，靠 `branches/` 子目录分隔。

**维护成本对照**：改一步的上下文 3 处 → **1 处**；改产出格式 4 处 → **2 处**（步骤文件 + 模板，测试自动跟随）；加一步 9 处 → **3 处**（新步骤文件、模板、README 目录树——后两项有测试兜底）。

## 2026-11-10 · 删掉归类步骤：类目归用户，不归本仓

**问题**：`steps/01-classify.md` 让一个独立 subagent 重读原文，只为了给每条内容打一个四选一标签（学习 / 借鉴 / 内容补充 / 可归档）。查引用发现这个标签**没有下游消费者**：`02-distil` 只看「有正文」标记（`:35`），`03-verify` 在 `reads` 里列了 `01-整理清单.md` 却全文不用，`04-confirm` 只读核查表。也就是说：一次完整上下文 + 一次原文重读 + 一个文件 + 一次交接，换来一列只有人看的字段。

**还有一层更根本的问题**：这套四选一是本仓替用户定的分类法。每个用户对网页内容的类目体系都不同，用户已有体系时，固定四类要么与之打架、要么被忽略。

**决定**：

1. **删掉 `01-classify.md` 与 `01-整理清单.md`**，流水线回到四步：采编 → 提炼 → 核查 → 确认（文件序号同步收为 `00`–`03`）。
2. **核查官不再读分类表**——`fresh` 上下文里最不该有的是与任务无关的表。
3. **去向挪到确认步**，按顺序取：用户 `AGENTS.local.md` 的「分类体系」段 → 知识库现有目录名 → 两者都没有才用兜底四类，并在提案里标明「这是兜底分类，建议定一套自己的」。提案新增「一、去向（按页）」表。
4. **提炼配额从「3~5 条」改成「最多 5 条，宁少勿凑」**——固定配额会逼薄页面凑数，而凑出来的条目还要花最贵的核查成本去核一段本不该存在的话。
5. 加一条断言 `test_taxonomy_is_user_owned`：四个兜底类目只许出现在 `03-confirm.md`，且该文件必须提到 `AGENTS.local.md` 与「兜底」。

**代价**：加一步时，00 与 03 由主会话做、01 与 02 起 subagent，四个文件而不是五个；分类从「流水线里的一步」降级为「确认时的一次判断」，因此不再有"先分类再提炼"的过滤——但那个过滤从来不存在（提炼只看有没有正文），所以并没有失去能力。

**复用判据**：一个步骤若产出没有下游消费者，它就不是步骤，是一个给人看的中间屏。屏幕要么并进相邻步骤，要么删掉。

## 2026-11-10 · 三条规则补位：判据归位、价值信号接通、回修有路径

用户问「还有什么是需要优化的」，逐条查引用后确认三处断线，逐条补上。

**一、`有正文` 的判据没有归属。** 它原来写在被删掉的归类步骤里（"低于 50 字符视为无正文"），删文件时一起丢了。而 `00-采编清单.md` 有这一列、`01-distil.md` 完全依赖它——写的人临场定，读的人当事实。判据必须跟着**产出**走（哪一步写这一列，判据就写在哪一步）。现落在 `steps/00-collect.md`：≥200 记 `有`、50–199 记 `有（疑截断）`、<50 记 `无`。

**二、`有（疑截断）` 是可信度封顶，不是内容标签。** 付费墙只抓到前段、懒加载只渲染首屏时，提取是残片，但笔记标注仍写 `原文`，核查通过就成了「直接引用」，与全文同等可信。现规定：`有正文` 为 `有（疑截断）` 的页面，所有条目一律按「转述源」封顶；提炼也不许从标题补。这与 OCR/ASR/Vision 降级是同一条原则——**你核到的只是"笔记忠实反映了这份残片"**。

**三、价值信号没接到确认步。** `01-笔记.md` 每条末尾的 `修订建议`（值得深读 / 参考写法 / 补充数据 / 可忽略）是流水线里唯一判断"值不值得留"的信号，而 `03-confirm.md` 全文没提过它。于是确认步只能按真假分堆，"这条根本不值得进知识库"无法表达。现规定：去向表的「依据」列必须引用修订建议原句；`可忽略` → 建议去向「不落库」。

**四、可疑条目有回修路径（方案 A）。** 原先 `grep 重跑|回修|重做` 全仓零命中：核查判「可疑」后只能由用户手工改，等于让用户替 AI 重写。现规定四步——只重做被标可疑的条目、只复检改动部分、最多回修两次、不许新增条目。整页重做会把已核过的条目拖回未核状态，是净损失，所以回修必须是"改错的"而不是"再写一遍"。

判据：**判据必须与产出同处一地；信号必须有人消费；标注必须能变成动作。** 三件事都可被测试断言（`test_body_threshold_is_owned_by_the_step` / `test_value_signal_reaches_confirmation` / `test_rework_path_is_defined`），不靠自觉。

## 2026-11-10 · 正文副本、落库命名、run 归档

用户问「还有什么是需要优化的」，剩余问题全在链的末端：采编之后、写进知识库之前。处理三条。

**一、正文副本（`runs/<run>/原文/<ID>.txt`）。** 原规定是「清单只记元信息，笔记匠和核查官按『原文来源』列去读原始文件」。对本地 PDF 成立，对网页不成立——那是**再抓一次 URL**。页面改版、付费墙收紧、登录态过期、内容被删，都会让核查官看到与笔记匠不同的东西，那时判「可疑」删掉的是无辜条目。三态判定的全部价值建立在"两个人看的是同一份字节"上，这条前提原先没有保证。

现改为：采编提取完就把正文原样落一份副本（纯文本、不加工），提炼与核查只读副本、不重抓；「原文来源」降级为出处标签。`runs/` 本就不进 git，代价只有本地磁盘。附带收益：跑完之后能回答"AI 当时到底看到了什么"——排查编造类问题的唯一原始证据。

**二、落库命名改用「标题 + 作者 + 平台」，且只约束 `Resources`。**（**已被 2026-11-11 的「命名反转」条目修订**：默认用原标题，重名时才加作者与平台，见文末。） 用户给的规则，理由是三者各自消歧：标题定内容、作者定归属、平台定来源版本（同一篇文章的转载、同作者的不同文章、同名的不同文章都不撞）。缺一不可、顺序固定，无署名写 `佚名`。目标已存在同名文件时**停下来问**（跳过 / 加日期 / 覆盖），不许自己选，尤其不许覆盖。

`Knowledge` 的知识笔记**不适用**这条——那是知识库自己的结构，按那边的规矩走；那边没规矩时问用户，不照抄 `Resources` 的格式。

**三、`runs/_archive/` 给跑完的 run 一个去处。** 原先 `runs/*` 全 gitignore、只增不减，一年后是几百个目录、没人知道哪个还能删。现在目录占位进 git（`.gitkeep`），内容仍不入仓，规则只是"跑完可以整目录挪进去"。

判据：**不可逆的一步（写进长期知识库）必须比可逆的步骤（写进 runs/）定义得更细。** 之前恰好相反。

## 2026-11-10 · 回修契约补全、条目号统一、工具冒烟

上一轮接上回修路径后留下的两处自相矛盾，加上工具层完全没有被执行过。

## 2026-11-10 · 提取工具的输出契约落到测试

`00-collect.md` 规定所有提取工具在 stdout 输出同一份 JSON（`success` / `text` / `char_count` / `method` / `error`），但此前没有任何断言——哪个脚本改了键名、或失败分支只吐一句散文，文档立刻变谎。

做法：对 7 个提取类工具各给一个「必然失败」的输入（不存在的文件、`file://` 假 URL、缺 API key），断言 stdout 最后一行是可解析 JSON、键集合**恰好**等于契约五点、`success=false`、`method=error`、`char_count=0`、`error` 非空。再补一条「磁盘上的 `extract-*.py` 必须都在用例表里」，防止新增工具绕过。

为什么用失败分支而不是成功分支：成功需要真实文件、bsk、API key、ffmpeg，CI 装不上；失败分支不依赖任何可选依赖，且在 CI 与本机行为一致。代价是不能证明成功路径的字段内容正确——那部分只能靠真跑一次人工验证，已经在 `runs/` 的历史产物里体现。

判据：**契约的价值在于失败时也不变形**——正常路径谁都会输出对，异常路径才是调用方唯一没法防御的地方。

## 2026-11-11 · 命名反转与边界切开：入口只到 runs/，之后归叠加层

用户三条指令（原话要点）：「不管是在 runs 里还是在 Resources 中，只有当标题名重复时才使用 `<标题> - <作者> - <平台>`，否则就直接使用原标题作为命名，同名也不需要停下来问我」「AGENTS.md 只能记 runs 往前的内容」「AGENTS.local.md 记 runs 之后的内容，其中对于从 Resources 提炼原子笔记到 Knowledge 需要再新建一个子代理来执行，且要遵循知识库中的 rules」。

**一、命名反转。** 旧规则是「标题必带作者与平台、三者缺一不可」。实际使用里多数页面标题本身已足够唯一，强制加后缀只是把文件名变长、把真名藏起来。新规则：

| 情况 | 文件名 |
|---|---|
| 标题未出现 | `<标题>.md` |
| 标题已存在 | `<标题> - <作者> - <平台>.md` |
| 仍重名 | 追加 ` - <YYYY-MM-DD>` |

同名**不停下来问**——旧规则把一次确定性操作变成了打断；覆盖仍然永远不许，所以升级是安全的。

**二、边界切开：入口只记到 `runs/` 为止。** `AGENTS.md` 是公开的、被任何工具读的；`AGENTS.local.md` 是本机叠加层。落库命名、写 `Resources` 的具体动作、`Resources → Knowledge` 的原子化，都发生在 `runs/<run>/03-待确认提案.md` 之后，属于本机约定，因此从 `03-confirm.md` 与入口里搬进叠加层，公开侧只留「确认前不碰知识库」与一句指针。

收益是两侧各自成立：干净克隆（没有叠加层）时，本仓仍能给出最小可用口径（原标题、重名才加后缀、不过问）；有叠加层时，落库细节与分类体系由使用者全权定义，本仓不猜。

**三、原子化必须是独立子代理。** `Resources → Knowledge` 是「把一篇原文压缩成一个概念」，与提炼/核查是同一种失败模式——自己压缩自己核对。所以在叠加层里规定：另起子代理、只读那一份 `Resources` 文件、不重抓不外搜、必须按 `<知识库根>/Rules/` 的层与分权写、一条笔记只装一个概念、冲突列出来问用户而不是改写已有笔记。

**代价**：`03-confirm.md` 不再是完全自足的——干净克隆下只能给最小口径，完整落库流程依赖叠加层。可接受，因为落库本来就是本机行为。

**判据**：**默认值要选"最短的那个"，例外才加长。** 旧规则把例外当成了默认，代价是每次落库都要多写两段没人读的信息。

## 2026-11-11 · 测试从「文件里有没有这行字」改成「产物能不能被下游消费」

**问题**。61 个断言里大半是 `assert "某句话" in 某文件`：它挡得住手抄表头抄错，挡不住
「核查表 12 条、提案汇总 9 条」这种真正会让用户看到错东西的问题——那类错这周发生过一次，
是人眼看出来的。而且它有两处永远测不到：LLM 判断对不对、提取工具的成功路径。

**决定**。

1. 新增 `tools/validate_run.py`（生产代码，不是测试辅助）：校验一份 run 的四份产物是否自洽——
   四份齐全、条数一致（正文↔核查表↔提案汇总）、条目号 `p<页>-<序>` 连续、三态与来源类型
   组合合法（转述源不能升格、可疑只能写 `—`）、笔记每条都有可解析出处、笔记与核查表对同一条
   的来源说法一致、提案把每条都归进了某一节且不重复、去向覆盖每一页。
2. 它在**两个真实位置**被调用：`03-confirm.md` 要求写完提案就验；`pre-push` 与 CI 跑 `--all`。
   这样它的价值不由「我是否记得写测试」维持——它是流程的一部分。
3. 测试改为验证校验器本身：一份干净 run 必须过，逐类注入真错必须被指出来。没有这层，
   校验器会退化成永远说 OK 的装饰品。
4. 抽出两个纯函数模块 `tools/naming.py`（三档命名与净化）与 `tools/safe_path.py`（跨盘相对路径），
   单独测。这两处是唯一会碰到真实文件系统的规则，出错后果是覆盖笔记或崩溃。
5. 补一条真成功路径：自己造一份最小 PDF，让 `extract-document.py` 真跑通（不联网、不要 key）。
   剩下需要 bsk / 模型 / ffmpeg 的成功分支仍然测不了，明说，不用假数据糊过去。
6. 删掉三条低价值断言：`test_tool_help_works`（3 条跳过）、`test_run_template_is_tracked_not_ignored`、
   `test_tool_imports_cleanly`——它们红了也说不清哪里坏了。

**代价**。`--all` 遇到旧版五文件结构的 run（`runs/2026-*` 那四个）会跳过而不是报错：
那批是存档，不该因为一次改名让钩子永远红。

**判据**。以后的验收口径不是「测试多少条」，而是**「校验器拦下过几次真错」**。
三个月内一次没拦到，就该把它删掉，而不是继续加断言。
